# The overnight prototyping engine

Point Mongoose at a project description and go to bed. It plans the build with the
local model, runs ~12 hours unattended, does the bulk of the work locally (free,
no permission prompts), farms the hard parts to Claude Code (metered, budget-
capped, with Mongoose granting permissions so Code never stops to ask you), and
leaves a morning brief on the bus. This is for rapid prototyping, not production.

## The two-tier model

Per step:
1. **Local model drafts** the files (qwen-coder, free, unlimited, no permissions).
   The local model does volume, not correctness.
2. **Claude Code reviews and fixes** the draft, headless, with Mongoose-granted
   permissions (`--permission-mode dontAsk`, the flag that actually runs without
   parking at a confirmation dialog). Bounded by a per-step timeout and a global
   Code-call budget.
3. **Check runs.** Pass -> git commit, advance. Fail -> block (no cascade).

So local keeps the night full and cheap; Code is the quality pass, capped so it
can't run away with your allowance.

## Autonomy and budget

- **Fully unattended:** `mongoose build-new "<description>" --auto-approve`. The
  local model writes the step plan AND the runner executes it. No human gate.
- **Code-call budget:** `BUILD_CODE_CALL_BUDGET` (default 40) or `--code-budget N`
  caps how many times Code is invoked this run. When exhausted, remaining steps
  run local-draft-only. This is a hard ceiling you set, not a guess at a fraction
  of your allowance (which Mongoose can't see).
- **Rate-limit backoff:** if Code reports a usage/rate limit, the runner stops
  escalating for the rest of the run and falls back to local-only, rather than
  hanging or wasting calls. Detected from Code's output and non-zero exit.
- **Per-step timeout:** `BUILD_STEP_TIMEOUT_S` (default 1800) so a stuck headless
  agent can't run forever.

## Why it won't "ask permission every 10 minutes"

Claude Code normally prompts before each file write or command. Mongoose invokes
it with `--permission-mode dontAsk`, the documented headless flag for scripted,
non-interactive runs. Mongoose is the supervisor; git is the undo button (every
passing step is a commit). Run it on a machine you're comfortable letting Code
edit freely within the build's repo dir.

## Setup (.env)

```
CLAUDE_CODE_CMD=claude          # or full path to the claude binary
BUILD_STEP_TIMEOUT_S=1800       # per-step ceiling (seconds)
BUILD_CODE_CALL_BUDGET=40       # max Code calls per run
```
The `claude` CLI must be installed and authenticated on the same machine.

## Workflow

```
# Fully unattended: plan + build overnight from a description
mongoose build-new "a FastAPI todo service with SQLite, tests, and a CLI" --auto-approve

# Or: plan now, review, then run (one-time approval)
mongoose build-new "..."                 # prints a plan id, awaiting approval
mongoose build-show <plan_id>            # see the steps + DAG
mongoose build-approve <plan_id>
mongoose build-run <plan_id> --code-budget 25

# Check progress / re-run to resume after blocks
mongoose builds
mongoose build-run <plan_id>             # done steps skip; blocked steps retry
```

Schedule `build-run` overnight with the same launchd pattern as the brief. The
morning brief surfaces the result; the bus has per-step detail; the repo is a git
history you review as a diff.

## RTM build source of truth

For Example Court/RTM work, keep **RTM operations** (demands, arrears, Metro reconciliation, payables, budget and evidence) separate from the **RTM product build** (WordPress/admin/Mongoose software being built). The canonical map is `docs/RTM_BUILD_SOURCE_OF_TRUTH.md`. Chat, UI, scheduler and Claude/Code peers must all report or advance the same persisted build plan/candidate state; none of them should become a hidden parallel source of truth.

## Honest limits

- The local model does volume; Claude Code does quality. With a tight budget,
  more steps finish as rough local drafts. Set the budget to match how much
  polish you want versus how much allowance to spend.
- A plan is only as good as its checks. Weak checks pass weak code. The local
  planner writes checks too, so review the plan once before trusting it unattended
  on something that matters.
- Prototyping, not production. Nothing here is a substitute for your own review
  before code does anything real.
- The real `claude`-driven run is environment-dependent (CLI version, auth,
  flags). First run will likely need a small adjustment to `CLAUDE_CODE_CMD` or
  the invocation; the orchestration logic itself is fully tested.

## Security: checks are model-generated

Step checks are generated by a local model and then EXECUTED. To contain the
risk, the runner only runs **structured checks** by default (a single
`python -m pytest ...`, `test -f/-d ...`, `ruff check`, or `python -c ...`,
each run without a shell). Checks that use shell features (`&&`, `|`, `;`,
redirection, subshells) are refused unless you pass
`--dangerously-allow-shell-checks`, and `--auto-approve` refuses outright any
plan containing a shell-shaped check. Local drafts are also path-contained to the
build repo (no writing outside it, no symlink traversal). Treat the build repo
dir as the trust boundary: run builds where you're comfortable letting generated
code and checks execute within that directory.

## Crash recovery and the time cap

A build run is bounded three ways: by `--code-budget` (Claude Code calls), by
per-step timeouts, and by a wall-clock ceiling `BUILD_RUN_MAX_SECONDS` (default
12h) / `--max-hours`. When the time cap is hit the run stops gracefully and posts
a summary; re-run `build-run` to continue.

If a run crashes mid-step, the step is left marked `running`. The next `build-run`
auto-recovers stale `running` steps (older than the step timeout + grace) back to
`failed` so they retry instead of being skipped forever. You can also recover
manually:

```
mongoose build-recover <plan_id>
```

Step checks are structured-only by default (pytest / test -f / test -d / ruff,
run without a shell). `python -c` and shell-feature checks are NOT in the safe
set: they are refused unless you pass `--dangerously-allow-shell-checks`, because
the check string is model-generated. Step ids are validated to a strict pattern
so they can't traverse the filesystem.

## Path containment on checks

In addition to refusing shell features and `python -c`, every path argument in a
structured check must resolve inside the build repo. A check like
`python -m pytest -q ../evil.py`, `test -f ../outside.txt`, or `ruff check ..` is
refused, so a model-generated check can't point at files outside the repo.

Note (honest limitation): a check can still run a test FILE the model wrote inside
the repo, which is code execution, just not shell or out-of-repo execution. For
fully untrusted use, the planned next step is named verifier functions Mongoose
implements itself, rather than model-generated command strings.

## Named verifiers (the safe success-check model)

Build steps declare success with a structured `verify` spec, NOT a command
string. The model picks a verifier by name and supplies arguments; Mongoose owns
what actually runs. There is no code path by which a model-authored string becomes
a command. Available verifiers:

- `{"type": "file_exists", "path": "src/app.py"}`
- `{"type": "dir_exists", "path": "tests"}`
- `{"type": "file_contains", "path": "README.md", "text": "Usage"}`
- `{"type": "pytest", "target": "tests/test_x.py"}`  (target optional = run all)
- `{"type": "ruff", "path": "."}`
- `{"type": "python_imports", "module": "myapp.core"}`  (module name validated)
- `{"type": "always_pass"}`  (only for genuinely unverifiable steps)

All paths are repo-relative and contained: a verifier cannot be pointed outside
the build repo, and `python_imports` validates the module name (identifiers and
dots only), so it is an import smoke test, not arbitrary code.

The legacy `check` string is still accepted for backward compatibility, but it is
not the safe path: it only runs if it is a safe structured check (or you pass
`--dangerously-allow-shell-checks`). New plans should use `verify`. The autonomous
planner now emits `verify` specs, and the Example Court plan uses them throughout.

### What this closes

Earlier audits flagged that "safe structured checks" were still model-generated
command strings (a model could write and then run a malicious test, or point a
check outside the repo). With named verifiers, the model no longer supplies a
command at all: it selects from a fixed allowlist and Mongoose constructs and runs
the check. This is the boundary required before trusting unattended overnight
builds on production-intent work.
